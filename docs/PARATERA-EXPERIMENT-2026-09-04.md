# Paratera 实际实验：运行链路完成，表示收益尚未成立

工作分支 `codex/retrieval-abstention`，起点 `16229b1`。本轮只增加实验执行/结果和测试，
不改变生产检索、结晶或知识更新算法，不发送真实用户收藏，不修改原冻结标签。

## 1. 本轮已经做到什么

在本机 WorkBuddy 模型配置中找到与 Paratera 端点绑定的凭据；环境变量中的
ANTHROPIC_AUTH_TOKEN 属于另一个供应商，没有混用或复制密钥。认证模型列表请求成功，
随后固定 `DeepSeek-V3.2-Instruct` 进行一次短生成探针，实际 HTTP 200、31 输入 token、
6 输出 token，确认能推理，不只是有配置。

本轮预算最多 50 次生成请求、150000 输入加输出 token，无自动重试。供应商没有返回
可核实单价，因此人民币金额仍未知；不能用 token 上限冒充供应商人民币账单硬限额。
输入预留按字节估计，回传 usage 逐次核对，缺失/矛盾即停止，不宣称已固定 tokenizer。

实际共 **49 次请求、23238 tokens**，包括首轮故障、探针和修订调用。没有超过本轮
调用/token 限制，没有在修订时重新开满额预算。构成如下：

| 部分 | 请求数 | 输入 + 输出 token |
|---|---:|---:|
| 探针 | 1 | 37 |
| 首轮抽取 | 6 | 2797 |
| 原文回答，之后按相同请求复用 | 12 | 4712 |
| 修订抽取 | 6 | 3020 |
| 普通文本卡回答 | 12 | 5494 |
| 结构卡回答 | 12 | 7178 |

## 2. 先保留失败，再作协议修订

首轮六次抽取都返回 JSON 代码块，原解析器只接受裸 JSON。同时抽取提示没有提供合法
方法 ID，模型返回 Method A/Method B，而解析器要求 A/B。两种卡片组因此没有发出回答
请求，但保留十二题分母；原文组不受影响。不能把这一失败解释为卡片表示没有价值。

首轮所有请求和原始返回已保留，见
[首轮结果](../evals/method-selection/runs/paratera-deepseek-v3.2-instruct-20260904-v1/result.json)。
修订仅明确抽取 ID，并增加所有组一致的完整外层 JSON 代码块解析；不改内部字段、
引用或选择，不把 Method A 人工替换成 A。重新抽取六次，原文请求未变故复用十二次
回答，仅新增二十四次卡片回答。修订 42 条响应中 40 条无需格式转换，2 条去除了外层
代码块；完整转换记录和原始响应分开保存。

这是看到失败后的开发修订，**不是独立复验、不是算法提升证据**。原实验的 inputs、
gold、protocol、runner 和 lock 均未覆盖。

## 3. 真实比较结果

来源为六个虚构包、十二题；一次模型运行，无独立留出。修订后的六个来源包都成功
形成卡片并实际发出两组回答；来源信息相同，两种卡片来自同一次中立抽取。
三组均没有超过 6000 字符上下文上限，但不是同 token 长度/预算的正式效果比较。

| 表示 | 方法选择正确 | 证据状态正确 | 引用定位有效 | 必需来源覆盖 | 独立使用总 token |
|---|---:|---:|---:|---:|---:|
| 原文 | 12/12 | 12/12 | 11/12 | 11/12 | 4712 |
| 普通文本卡 | 11/12 | 10/12 | 11/12 | 11/12 | 8514 |
| 结构卡 | 11/12 | 10/12 | 11/12 | 11/12 | 10198 |

卡片总量各自承担完整的 3020 构建 token，不因实验共用抽取而除以二；不含首轮接口
调试开销和探针，这些已经计入本轮总消耗。当前原文很短，卡片增加字段、拆分和重复
引用后反而更长，不能将该成本关系直接推广到长文或不同重复查询场景。

**本轮没有观察到结构卡优于条件完整的普通文本卡，两种卡片也没有胜过原文。**
不能因此推断所有结构表示无效；但当前没有依据继续投入“仅换成 JSON”的优化。
引用可定位不等于语义支持；正确选择和管线 error 也分开，不能把每组 1 个管线/引用
失败解释为只有 1 个语义错误。

机器结果见[修订评分](../evals/method-selection/runs/paratera-deepseek-v3.2-instruct-20260904-repair-v1/result.json)
与[用量](../evals/method-selection/runs/paratera-deepseek-v3.2-instruct-20260904-repair-v1/usage.json)。

## 4. 值得进入下一轮的具体失败

### q10：一个方法的冲突影响了另一个方法

两份报告只对 A 的延迟不一致，对 B 均报告 90 ms；任务仅问 B 是否低于 100 ms。
两种卡片回答都承认 B 为 90 ms，却因 A 有冲突而弃答。原文组正确选择 B。
这是本轮明确观察到的无关冲突影响决策，不证明已确定单一因果归因，也不靠修改 gold 修正。

下一轮要测：先限定任务所问的方法/版本/条件，再在对应证据范围内判断冲突，能否减少
此类误拒，同时不漏掉真正相关的冲突。普通文本也给同样的范围限定，避免弱化基线。

### q12：条件不满足，不等于来源相互矛盾

任务只有 4 GB RAM，方法要求至少 8 GB。两种卡片都正确弃答，但把状态写成 conflict，
不是 explicit_negative。解释文字本身承认是资源要求不满足。后续协议应明确区分
“证据之间矛盾”与“方法不满足用户条件”，防止分类术语本身含糊。

### q07 / b04：缺失信息与测量范围没有被准确保留

原文明确说未报告加密或延迟数据，抽取卡丢掉这句话。卡片组仍正确判定加密证据不足，
但引用为空，按当前引用契约失败；这不是产生加密支持幻觉。后续需要单独讨论证据不足
时如何提供可审计依据，不能靠强制随便引用一句无关话来提高引用率。

b04 把“压缩比未在实时流上测量”的范围放进条件，写为 not on live streams；它容易
被读成适用性禁止，而原文只限定测量范围。这是人工查看发现的潜在过度解释，当前
十二题没有直接测它，不计入正式语义错误率。新增对应诊断题，不回改本轮答案。

### q11：意思相近也不能伪装成原文连续引用

原文组把同一来源内两句不相邻的话拼成一个 quote，唯一原文片段校验正确拒绝。
后续若需要引用多个片段，应使用多个引用项；不把拼接字符串伪装成原文。

## 5. 下一阶段主要做实验，而非扩展产品面

优先级如下，仍按“用户任务—能力流程—代码模块”管理：

1. 固化以上失败为开发回归，明确条件类型、冲突作用范围和引用契约。只为可测的失败
   增加最小规则/表示，不先扩大通用 schema、图谱或更多 feature。
2. 建新实验版本：新增来源包和不重复原题结构的任务，包含长文干扰、无关方法冲突、
   测量范围/适用条件、版本切换。固定模型 tokenizer、输入约束和评分定义；当前十二
   题只作已知失败回归，不能再标成盲测。用清晰文本作为强基线。
3. 对一个窄改动做消融：例如是否按方法/条件限定证据范围。记录错误适用、误弃答、
   引用支持和实际用量，不只比较 JSON 与文本。另设人工审核范围，不让模型自判一切。
4. 只有任务收益与成本方向明确后，再进入增量更新的全量重建/局部重算对照。
   检索真实 embedding 尚未在本轮测试；本轮不能证明全部“三条算法路径”已经验证。

下一轮开调用前重新明确预算。本轮还剩调用额度不构成继续刷分或扩大试验的理由。
