# 从可靠记忆到可使用的知识：研究范围与证据

日期：2026-09-04。接续 [产品共识](PRODUCT-DESIGN-INDEX.md)，纠正“有三条路径就有三项
创新”的误读，并把知识表示、知识挖掘纳入研究视野。本轮不新增产品功能或更改排序参数。

## 1. 先把“创新”说清楚

三条核心算法路径是**检索、结晶、增量演化**，这是对系统职责的划分，不是原创性计数。
先前把若干设计点直接列为“创新点”过于宽泛，今后区分以下层次：

| 层次 | Sheaf 中的例子 | 可以说明什么 | 不能据此声称什么 |
|---|---|---|---|
| 复用的基础方法 | BM25、向量相似度、哈希、幂等、锁、原子替换 | 实现选择与工程掌握 | 发明这些方法 |
| 具体系统设计 | 排序与拒答分开、证据身份细化、授权与评分分开、领域内原子执行 | 识别并解决本产品约束，能解释取舍 | 学术上首次提出 |
| 待验证的方法贡献 | 在预算内保留适用条件与证据；按证据变化局部更新 | 一个可明确比较的研究假设 | 已经更准、更省或更有用 |
| 已有实验结论 | 固定代码在某个冻结集合上的逐例结果 | 该分布、后端、版本内的观察 | 无条件泛化、产品成立、论文创新已证 |

实验不是创新的来源证明。证明链应该是：已有方法解决到哪里 → 本任务有哪个具体缺口 →
提出何种机制 → 与合理基线比较 → 拆掉组件检验原因 → 看代价、失败与泛化。
文献比较负责“与已有方法有何不同”，实验负责“这个不同有什么用”。二者不能替代。

面试目标也不必等同论文发表：一个诚实的负结果、能重现的失败、据此作出的设计选择，
可以展示算法判断能力。相反，不能把写了复杂系统或用了三个名词当成三个新算法。

## 2. 不把产品收窄成一个更新执行器

较完整的产品问题是：**用户挑选的资料，怎样变成可检索、可组合、可核验、会随证据
变化的个人知识，进而帮助 Agent 完成任务？**

“新资料来了旧结论要不要改”是这个问题中目前边界较清晰、工程基础较强的一条线，
不是全部愿景。收藏表达偏好，不代表用户赞同每句话，更不代表来源必然正确。
主动收藏能否改善实际任务效果、用户是否反复使用，仍是产品假设。

知识表示横跨三条路径，不需要再称“第四驾马车”：它决定系统拿什么来检索、如何组合
结论、更新时定位哪些对象。知识挖掘则对应用户的问题与输出任务，不先绑定为某一种算法。

## 3. 当前代码到底走到了哪里

本次核对的生产基线为 `4b2326a`。以下不是未来设计图：

| 层 | 当前已有 | 仍缺少 |
|---|---|---|
| 原始资料 | raw 文本、Entry、摘要及结构摘要、来源与指纹 | 信息是否在进入模型前完整保留，需要按路径测量 |
| 普通知识卡 | claim/evidence 文本、卡级来源集合、无类型关联、可扩展 extra | 受验证的适用条件、有效期、逐主张证据配对、关系类型 |
| 证据版本 | CardVersion、parent revisions、EvidenceRef、quote/span、争议状态、fact key/value、授权快照 | 自由文本原子化、条件比较、语义支持判断与动作选择 |
| 对外使用 | 版本可投影成普通卡；有列表、搜索、渲染 | 常规结晶/搜索未自动接入完整版本账本；消费视图不保证携带全部治理信息 |

核对入口：

- `sheaf_ai/storage.py:329`：Entry/raw 保存边界。
- `sheaf_cards/base.py:123`：KnowledgeCard；`save()` 同 ID 更新不等于版本历史。
- `sheaf_ai/_evidence_memory_models.py:182`：EvidenceRef；`:416`：CardVersion。
- `sheaf_ai/card_service.py:620`：版本投影；`:958` 附近：普通卡路径委托。
- `sheaf_ai/crystallize.py:162`：选段 manifest；`card_extraction.py:504`：卡片构造。
- `sheaf_ai/renderer.py:38`、`:166`：字段可见性与 claim 截断。
- `sheaf_cards/embeddings.py:149`：卡向量文本仅使用 title/claim/evidence/tags。

必须保留的边界：

- `atomic claim` 的身份计算不等于已经实现自动原子主张抽取。
- `authority scope` 表示谁有权纠错，不是某个结论在什么条件下成立。
- quote/span 可定位不等于该段文字蕴含结论。
- 不同 fact value 可触发规则，不等于系统理解了自由文本中的否定、例外或不同适用范围。
- 普通卡 provenance 记录生成信息，不等于逐主张保存了本轮选段清单和引用位置。
- 关联 ID 不等于因果、对立或时间关系；信息放进 extra 也不等于检索和 Agent 消费会使用它。

所以，“已经不只是 schema”与“表示方法尚未被证明有效”可以同时成立。

## 4. 表示的研究空间：不是字段越多越好

一个人为示例（不是领域事实）：

> 方法 A 在离线批处理中降低成本，但不适用于要求即时反馈的任务；证据来自来源 1
> 的某段实验，来源 2 只复述了来源 1。

把它压成“方法 A 更便宜”丢了适用条件；把两个 URL 计作两次确认又丢了依赖关系。
即使卡片存全了，输出时裁掉句尾，Agent 仍可能拿到失真的结论。真正的问题涵盖：

1. **抽取**：能否把结论、条件、例外和证据正确分开？
2. **组织**：哪些结论可以合并，哪些只是在不同条件下成立，哪些真正冲突？
3. **选择**：当前任务只需要哪些知识；预算不够时哪些内容不能丢？
4. **维护**：来源变化后，哪些结论需要重查，哪些应保持不动？

一个值得测的假设 H1：在指定任务族、相同模型与上下文预算下，保留适用条件和可定位
证据的知识单元，比原文块或扁平卡片减少适用性错误，并且额外构建和更新成本可接受。

H1 未被当前测试证明。可能的反例包括：普通文本卡已足够；结构抽取错误抵消收益；
生成结构的费用大于节省的上下文；只在模板化问题有效。实验必须允许这些结论出现。

“高效”至少要同时看任务正确性、上下文开销、构建成本、更新成本与维护复杂度，不能
只展示 JSON 更短。没有模型 tokenizer 时只能报告字符数，不能称 token 成本。

### 可以借鉴什么

这些只是代表性方向，不是完整新颖性审查：

- PROV-DM 已有派生与修订概念；不需要重新发明通用来源词汇。
  [W3C PROV-DM](https://www.w3.org/TR/2013/REC-prov-dm-20130430/#component2)
- RAPTOR 的摘要介绍了不同抽象层次的摘要树，可以启发粒度选择。
  [RAPTOR](https://arxiv.org/abs/2401.18059v1)
- GraphRAG 的摘要面向全库主题问题，以实体图和社区摘要组织资料。
  [GraphRAG](https://arxiv.org/abs/2404.16130v2)
- HippoRAG 的摘要展示了图结构与已有图算法结合进行知识整合的方向。
  [HippoRAG](https://arxiv.org/abs/2405.14831v3)

后三项目前仅核对摘要，不引用效果数值，不声称 Sheaf 已与其公平对比，更不能由此推断
“别人没有做条件或更新”。若 H1 进入正式研究，还要精读这些工作与更直接相关的条件、
时间、冲突及记忆压缩研究，补齐更近期工作。阅读证据与未决标记见
[小型证据账本](research/representation-2026-09-04/README.md)。

## 5. 知识挖掘：从用户要做什么来选择

当前结晶是多来源综合生成；`insights.py` 主要靠标签、收集日期、词重叠提供关联；
`matrix.py` 是事件相关报道与角度表。`mcp/verify.py` 确有模型比较摘要的实现，但尚不
核实逐主张原文 span。不能把这些统称为已验证的知识发现。

可保留在探索列表中的三种任务是：

| 用户任务 | 可能的有用输出 | 首要验证问题 |
|---|---|---|
| 选方法/做方案 | 方法、适用条件、代价、证据的对照 | 是否少选了不适用方案，而不只是表格更丰富？ |
| 解释分歧 | 哪些来源真冲突，哪些只是对象/时间/条件不同 | 是否减少假冲突与误合并？ |
| 找下一步要查什么 | 缺失证据、尚不能下结论的问题 | 是否比泛泛“延伸阅读”更能改变下一步行动？ |

这三项是待选择的用户任务，不是本轮立刻扩展的三个 feature。无边界关联生成容易产生
看起来新颖但不可核验的输出，因此先将“有用”绑定到任务与证据，不把惊喜感当正确性。

## 6. 下一轮实验怎样避免自证

本轮只做两项无用户诊断：冻结代码后新写检索样本；真实卡片通道的信息保留诊断。
后者测传输损失，不评价模型抽取和理解。结果入口：

- [新检索集](../evals/retrieval-prospective/README.md)
- [表示边界诊断](../evals/representation-boundary/README.md)

后续顺序如下，每步有独立退出条件：

| 步骤 | 工作 | 退出条件 |
|---|---|---|
| R0：定位损失 | 原文/模型响应/卡存储/视图/索引逐层检查；新检索样本固定参数 | 可重跑逐例原始输出，区分语义错误与字段传输错误 |
| R1：最小接通 | 依据损失修复消费边界；明确普通卡与版本卡的统一读取和来源映射契约 | 来源、条件、争议状态不静默消失；旧卡兼容；失败可诊断 |
| R2：表示效果 | 一种用户任务，比较原文块、条件完整的普通文本卡、结构知识单元 | 固定模型与预算；支持性、条件遗漏、错误适用和实际费用都报告 |
| R3：演化效果 | 固定证据序列，比较全量重建与只重算受影响知识 | 变化正确率、无关知识保持率、误更新率、总更新成本 |
| R4：任务驱动挖掘 | 只选择一类对照/分歧/证据缺口任务 | 任务结果有独立判定，不用模型自报“新颖度”当成事实 |

R1 是实现建议，不是本轮已完成；R2–R4 未开始，不在未验证的表示上同时扩功能。

R2 预先要固定的公平条件：

- 数据按来源 bundle/主题分组切分，近似改写或转载不得跨开发与测试泄漏。
- 不让结构组看到 gold 或更多原文；不把人工理想卡对比机器摘要。
- 给普通文本基线相同的条件/证据保留要求；否则测到的可能只是提示词差异。
- 同一模型、温度、源信息与输入 token 预算；同时保存原生无截断视图和预算视图。
- 测原文支持率、条件遗漏率、不可用方案选择率、冲突误判、拒答，以及构建/查询/更新费用。
- 消融条件字段、证据映射与更新依赖时，其余输入保持一致。用重复运行和区间表示小样本不确定性。
- 不把人工标注直接作为被测系统的抽取结果。标注只用于评估；真实模型响应完整封存。
- 查看过失败后，这一版测试集转为诊断回归；新主张需要新的留出来源和任务。

## 7. 与面试及第二章的关系

面试主线可以是：从主动收藏的资料库出发，发现简单检索/摘要不足以保证任务适用性，
把证据选择、知识表示和变化维护拆成可测问题，报告哪些改进有效、哪些只完成了机制。
不需要声称从零发明 BM25 或 PageRank，也不需要每个模块都贴一个创新标签。

第二章如果继续研究领域任务中的知识表示，应单独定义领域约束、规划错误和评价任务。
Sheaf 可以承载实验，但通用软件上的诊断不能自动成为遥感方法或学位论文贡献；本轮
没有重新审核最新论文稿，也没有把原来的卡片 schema 自动升级为已证方法。

研发管理上仍沿用“用户任务—能力流—代码模块”。每轮同时交付实现证据和研究决策：
明确本轮学到了什么、哪个假设被否定、为何下一步值得做。保持较宽的问题视野，但只
选少量可证伪的实验推进，避免局部指标无限打磨，也避免同时铺开整个知识管理平台。
