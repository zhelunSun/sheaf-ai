# Sheaf 核心研发工作方式

> 适用范围：检索、结晶、增量知识演化，以及支撑它们的来源治理和持久化。
> 目标不是增加流程，而是让并行开发更快，同时让实验结论经得起复查。

## 1. 一轮工作的固定顺序

### 1.1 先做只读审查

先复现问题、指出真实生产路径、列出失败样本和当前边界，不立即修改代码。审查输出
必须区分四件事：

- 产品希望解决什么问题；
- 代码目前真正保证什么；
- 实验目前真正证明什么；
- 哪些仍只是下一步假设。

这样可以避免在实现过程中不断改变问题定义，也避免把一个机制测试写成效果结论。

### 1.2 冻结最小契约

编码前固定输入、输出、不变量、失败方式和验收证据。阈值只允许从开发集选择；已经
查看过答案的样本只能作为诊断回归，不能重新包装成盲测结果。发现负结果时保留它，
下一轮以失败切片驱动改动。

### 1.3 按边界并行，而不是按人数并行

每条并行线拥有不重叠的文件和清晰接口。例如：算法线负责排序与拒答，治理线负责
注册表和解析器，事务线负责领域账本；主线负责生产适配、交叉测试和文档。共享文件
由主线最后集成，避免多条线同时改一个核心模块。

### 1.4 先定向验证，再交叉攻击

实现者先跑自己负责的机制测试。随后由没有写这段代码的人从相反方向检查：伪造输入、
损坏文件、重复请求、进程中断、并发竞争、降级后端和无答案请求。修复必须落成可重复
测试，不能只留下评审意见。

交叉复核最好由另一条线完成，因为实现者最容易沿着自己已经相信的契约继续检查。
本轮的有效做法是：让检索实现者攻击来源治理，让治理实现者攻击事务边界，再让没有
参与算法实现的人检查评测泄漏与多语言反例。复核优先寻找“绿测仍可能绕过”的路径，
而不是重复阅读正常流程。

### 1.5 最后统一收口

主线依次运行定向测试、完整测试、静态检查、离线评测、构建和安装烟测。文档只更新
为这些证据支持的状态，再提交一个阶段性 commit。实验资产和产品代码可以分 commit，
但两者都必须能独立解释为什么存在。

## 2. 测试证据阶梯

| 层级 | 回答的问题 | 典型证据 |
|---|---|---|
| 机制测试 | 单个规则是否按定义执行？ | schema、reason code、状态转移 |
| 性质测试 | 输入变化时不变量是否保持？ | 顺序变化、等价表达、重复请求、扰动测试 |
| 故障测试 | 失败是否留下半成品？ | 崩溃点、原子替换、并发 CAS、腐败文件 |
| 冻结离线评测 | 固定样本上的相对效果如何？ | manifest、开发/留出分离、消融、负结果 |
| 真实模型评测 | 外部模型下效果和成本如何？ | 固定模型参数、原始响应、延迟、token、失败率 |
| 用户验证 | 产品是否真的产生持续价值？ | 可回溯的实际复用、纠错行为和访谈证据 |

较低层通过不能代替较高层。例如，原子写测试不能证明自动演化策略正确；冻结合成集
提升也不能证明用户愿意付费。

## 3. 三条必须长期保留的纪律

### 3.1 评分不是授权

来源质量分、模型判断和用户偏好可以帮助排序，但不能自动签发官方纠错、独立观察或
其他治理权限。授权必须来自独立、可审计并绑定具体内容的入口。

### 3.2 排序不是拒答

相对归一化分数适合决定谁排在前面，却无法证明库里存在答案。检索的候选排序与
query-level 是否回答必须分开评估，拒答应给出可检查的绝对支持原因。

### 3.3 恢复语义必须与原子范围一致

一个文件内的一次原子替换可以宣称“该领域写入全有或全无”。多个文件之间没有共同
事务时，只能宣称“通过收据或日志可恢复”，不能称为跨文件原子事务。

### 3.4 指纹必须绑定真正执行的内容

请求哈希只证明“曾经批准过一个请求”，不能证明执行器后来提交的仍是同一组操作。
涉及延迟执行、重试或恢复时，应另算执行计划指纹，把操作内容、证据、目标版本、策略
版本和幂等键一起绑定；恢复时逐项核对持久化回执。只比较 decision id 或请求哈希，
仍可能让被替换的操作借用旧授权。

### 3.5 评测输入只暴露运行时真正可见的信息

“先生成排序、后加载 qrels”还不够。如果 query 文件本身带有 no-answer、类别或难度
标签，算法接口仍然有机会看到答案。ranker-visible fixture 只保留产品运行时可获得的
字段；答案标签放进 evaluator-only 文件，并用测试直接断言传给算法的字段集合。

### 3.6 先确定作用域，再截断候选

过滤条件定义的是问题作用域，不是结果展示选项。应先校验并应用过滤，再进行召回、
融合和拒答；最终返回条数不能改变系统对“库里是否有答案”的判断。无效过滤应明确
失败关闭，不能静默退回未过滤结果。

### 3.7 三条算法路径不是三项原创算法

每项对外主张分开标明：复用方法、系统设计、待测假设、实验结论。引用已有工作说明
差异，实验验证效用；通过测试不自动证明原创。摘要级阅读不能升级为完整新颖性审查。

### 3.8 新样本必须先固定被测代码

新合成样本尽量由没有读当前算法实现和旧 gold 的协作者编写；先记录代码 hash、
固定参数、评价口径，再写样本。记录这种隔离的局限，不能称独立外部盲测。主线看过
失败样本后，不改 gold、不回填旧结果；改算法必须开新版本，旧集只作诊断回归。

### 3.9 表示能力必须沿真实消费路径测量

不能用人工理想卡片证明模型抽取能力，也不能用字段存在证明 Agent 已使用它。
分开检查抽取、存储、渲染和索引，保存实际文本；未知字段探针与已支持字段分组计分。
字符数不是 token 数，信息出现率不是语义正确率，传输诊断不是任务效果实验。

### 3.10 Windows 回归固定子进程编码

2026-09-04 普通 pytest 运行在跨进程测试处触发输出捕获的 UnicodeDecodeError，并造成
后续大量 setup/teardown 连锁错误。单独重跑该测试以及统一 UTF-8 后的完整回归均通过。
保留原失败记录，不把捕获层连锁错误解释为大量独立业务缺陷，也不以跳过测试解决。
本机复现命令：

```powershell
$env:PYTHONUTF8 = '1'
$env:PYTHONIOENCODING = 'utf-8'
python -m pytest tests -q -x
```

这些设置只作用于执行该命令的进程环境，不修改用户的持久系统设置。

### 3.11 展示、追踪与判断分别验收

完整卡片不应静默截断适用条件；显式列表预览必须给出完整卡 ID。原始 `[Source N]`
引用编号属于提取时的整个来源包，不能用 card.source_ids 子集重新编号。映射缺失应
明确 unresolved，片段选择记录不能被包装成语义支持证明或来源授权。

检索有结果只表示有候选。严格拒绝和待核对检查通路分开，警告必须穿过 CLI/HTTP/MCP
及文本客户端；不能让内核诊断在接口层静默消失。修复后同集指标只能叫已知标签回归，
必须同时报告找回正确资料和多返回不支持问题前提的资料，不能只报 Recall 改善。

### 3.12 完整回归暴露的新故障要单独收口

2026-09-04 修复轮的跨进程 CardStore 测试出现真实 WinError 5，不同于前次编码错误。
补充 Windows 特定替换错误的有限重试，继续持有写锁，不重做整笔业务、不删除旧文件；
永久失败仍显式报错。使用故障注入验证失败不破坏旧文件，再跑真实跨进程测试。
具体占用者未查明时，不把杀毒软件等可能原因写成已确认根因。

### 3.13 状态含义和实验分母不能在适配中改变

版本创建时 active，不代表读取历史时仍是当前 head。投影应同时保留创建时状态与当前
被替代状态，不改历史事件。字段筛选不能静默剥离内置视图的治理提示；元数据矛盾必须
显式可见，renderer 不重读账本时也不保证实时性。

方法实验中，抽取失败不应连原文基线也停止；所有组保留同一任务分母，不仅报告成功
样本。字符预算不是 token 预算；导入响应的模型 ID/hash 是一致性记录，不是独立认证。
正式全量回归和冻结实验运行期间停止编辑被测源码。源码一致性保护中止时，保留中止
原因并重跑，不禁用保护以获得绿色结果。

## 4. 一轮开发的退出清单

- 生产路径和评测路径调用同一核心实现；
- 失败样本已固化，且没有把看过的留出集当成新盲测；
- 新持久化格式有旧版本重放、损坏检测和写后降级说明；
- 新阈值有开发集或明确规则依据，并带版本号；
- 并发、幂等和故障后的状态有可重复测试；
- README、设计文档和演示话术没有超过实验结论；
- 完整测试、静态检查、离线评测和构建结果已记录；
- 下一轮只保留最重要的失败切片，不把所有想法同时升级为主路线。
